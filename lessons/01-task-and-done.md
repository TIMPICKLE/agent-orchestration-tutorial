# 01 一个任务怎样才算完成

[学习路线](../README.md) · [下一课](02-control.md)

## 本课只解决一个问题

在讨论 Agent 怎样思考之前，先写清楚：你到底希望它完成什么。

假设你说：“修复工单 1042。”这句话对人已经不够明确，对 Agent 更不够。它可能只找出原因，也可能改了代码却没运行测试，还可能直接把修复发布到线上。这些结果的风险和价值完全不同。

先把任务拆成四项：输入、交付物、验收证据、权限。

- 输入：工单描述、指定代码版本、允许读取的上下文。
- 交付物：一份限定范围的补丁及解释。
- 验收证据：复现测试先失败，修复后通过，已有回归测试没有出现新增失败。
- 权限：允许在隔离工作区修改和测试；发布代码需要授权；不允许自行部署生产。

这里的“验收证据”非常关键。`Agent 回复：已经修好了` 是一个陈述。指定版本上的测试命令、退出码、输出摘要，是能被检查的记录。两者不等价。

## 把模糊目标改成一个任务契约

下面是教学用的任务卡，并非你的仓库现有 API：

```yaml
task_id: demo-1042
goal: 正确解析带千分位的金额字符串
base_revision: demo-base-v1
allowed_actions:
  - read_repository
  - edit_in_workspace
  - run_unit_tests
deliverable: patch_and_test_report
done_when:
  - target_test_passes
  - regression_tests_pass
  - patch_scope_is_reviewed
stop_when:
  - needs_new_permission
  - repair_budget_exhausted
```

逐项理解：`goal` 描述用户要的结果；`base_revision` 固定输入版本；`allowed_actions` 约束执行；`done_when` 说明凭什么完成；`stop_when` 说明什么时候应停止尝试并交还问题。

不要一开始就追求完美通用的任务格式。先为一个真实任务写出这几项。如果写不出来，换框架也不会替你补齐需求。

## 完成和停止是两回事

“测试通过”可能意味着成功；“预算用尽”意味着应该停下；“等你确认是否发布”意味着暂停。三种情况都可能让当前进程不再执行，但绝不能统一标记成 `done`。

可以先使用四个直观状态：`running`、`waiting_for_human`、`succeeded`、`failed`。后续再按需要细分，不必一开始造几十种状态。

更细一点：即使测试通过，也只能支持测试所覆盖的行为。它不能证明程序绝无漏洞，更不能自动证明你允许部署。**质量判断和操作授权要各自成立。**

## 两种设计为什么都需要这一步

无论外层 Python 控制所有步骤，还是让 Claude 在会话里自行规划，你仍然需要相同的任务契约。区别只是契约由谁执行、哪些字段由哪个系统强制检查。

后面读到 `DoneCriteria` 时，把它理解为这个问题的工程实现之一。先理解问题，再看类名。

## 小练习

把“帮我把 bug 修好并告诉我”改写成五句话：允许改哪里、交付什么、怎样验证、何时问人、怎样通知。

如果你的答案里出现“完成后”，再问一句：完成由什么可检查的证据决定？

**带走一句话：先定义什么是完成，才有办法设计怎样自主工作。**
