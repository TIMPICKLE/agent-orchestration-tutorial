讲解备注 从业务动作，展开到职责划分

把业务流程转成 Agent 工作流时，先判断每个环节需要什么性质的决策。查询参数明确、创建 PR 的接口确定，就可以用程序表达。定位问题和选择修复方案依赖代码上下文，适合保留探索空间。

涉及验收、授权和合并时，检查可以自动执行，责任人仍需要明确。角色名称本身不足以形成工作流，还要约定节点之间交换什么，以及什么时候结束。

这里是一种设计方法，不表示当前系统每个工具已经按此严格隔离。现场可以选一项日常任务，让听众逐步判断各个环节属于哪一类。

讲解备注 把“完成”变成可检查的约定

输入里的代码基线明确任务从哪个版本开始。交付物告诉下游接收什么。验收证据则说明这份交付经过了哪些检查，以及检查对应哪个代码版本。

如果 Agent 发现需要改动另一个未授权仓库才能继续，它应报告阻塞，说明缺少什么、已经完成什么、由谁接手。阻塞也是可以约定的任务结果，不能一律折算为成功。

本页是设计示例，不宣称当前项目已经完整实现这些字段。复制的模板包含待填写项，需要按真实任务补充。

当前实现：MAF 版的外层仍由 Python 顺序编排。工具内部的提交、推送等副作用需要单独检查。

讲解备注 沿着真实调用链追踪控制权

外层程序负责准备、调用修复、接收结果和后续交付。内层根据问题读取代码，选择工具，修改后再根据工具反馈决定下一步。外层不需要提前列出每一次文件读取。

这张图表达职责分工，不能用它代替权限审查。一个名为“修复”的工具，内部也可能包含提交和推送。应追问：谁选择了这个工具，它会产生哪些副作用，哪些条件由程序检查？

现有顺序编排与内层工具循环已经可以合作。复杂路由、持久恢复属于需要另行设计的能力。

一次修改之后，新的观察决定继续、交付还是停止。

  1. 01 / READ读取上下文

    问题、代码与既有状态

  2. 02 / ACT选择并执行工具

    在允许范围内行动

  3. 03 / OBSERVE观察结果

  4. 04 / DECIDE调整与退出判断

    验收、阻塞、权限、预算

未满足验收且仍可执行时，将反馈带入下一轮
读取：定位异味涉及的代码

教学演示，不调用模型，不修改仓库。

第 1 / 4 步

停止条件属于循环设计的一部分。

讲解备注 通过三个结果，解释反馈与退出

当修改后的测试断言失败，原样重复同一个动作通常不会增加信息，需要根据反馈调整候选方案。若验证通过，就继续检查是否满足任务约定。若预算耗尽，即使仍有想法，也应停止并留下可接手的结果。

此演示固定展示三种路径，用来解释机制。它不是当前生产任务的运行记录，也不是完整的执行协议。真实系统需要在合适的执行点检查权限和预算，尤其是在产生副作用之前。

工具结果应尽量包含可识别的状态、产物引用和错误类型。一次“测试通过”也只覆盖那次测试的范围。

05 / 10设计建议

Agent 的能力边界与权限控制

把“可以自主修复”，细化成允许的动作、范围与预算。

任务内部

  • 指定仓库读、改、测工作区范围与可修改文件
  • 工具名单与参数范围执行前检查实际动作
  • 时间、轮数与成本预算达到上限后停止并报告

外部动作

  • 推送、合并、发布分别定义授权条件
  • 受控执行器操作落实凭据范围、参数检查和执行策略
  • 超出授权时转交说明阻塞原因与所需决定

提示词表达意图，工具端落实限制。

讲解备注 检查真正产生副作用的位置

明确授权的动作可以自动完成，不要求每一步都现场点击确认。重点是授权范围能够表达，执行端能够检查，越界之后有清楚的停止和升级方式。

Skills 和提示词适合提供规范与工作方法，但它们不会自动限制凭据或文件系统权限。真正产生副作用的是工具及运行环境，因此工作区隔离、工具参数检查和预算也要在这一层落实。

本页属于设计建议。项目中的真实限制需要结合 CLI 参数、工具实现和部署环境逐项核实。

讲解备注 从组件名称，回到实际责任

Workflow 管理业务阶段，Agent 在给定任务内选择行动，Tool 执行具体操作。Skills 提供指导，MCP 提供系统连接协议，Harness 概括执行所需的运行支撑。它们不一定对应独立服务，也不要求全部采用。

连接出的工具仍需自己的权限策略。把约束写进 Skills，也不等于工具端已经强制执行。评审时可以追问：规范如何进入上下文，工具结果如何回到循环，业务状态由谁保存？

本页按教程与项目语境给出工作性定义，用来帮助分工，不主张这些术语在所有框架中都有完全相同的边界。

讲解备注 保存了记录，不等于已经可靠恢复

上下文服务推理，任务状态服务流程，日志服务追溯。三者会引用相同的信息，但承担的责任不同。恢复过程需要清楚知道哪些状态已持久化，以及哪些远端动作可能已经发生。

如果创建 PR 的响应丢失，应先查询远端，而不是立即重复创建。稳定的任务标识、产物版本、阶段提交点与幂等约定，才能为恢复提供可靠依据。

当前项目有 WorkflowState 和 JSON 记录，但不能据此声称已经具备可靠的跨进程恢复。人工中断与恢复属于后续设计方向。

08 / 10设计取舍

多 Agent 的拆分依据与协作成本

准备增加一个 Reviewer 前，先明确它能带来什么可验证的收益。

拆分的理由

责任可以独立

  • 子任务可独立验证产物和验收能够单独定义
  • 上下文或权限需要隔离避免无关信息与过大的权限范围
  • 工作可以真正并行依赖关系允许独立推进
增加的成本

协作需要协议

  • 交接信息背景、产物与证据如何传递
  • 协调冲突共享工作区与冲突由谁处理
  • 调用与等待模型成本、延迟和失败链路

加一个 Reviewer 后，漏检是否真的减少？

子图与多 Agent 并行属于设计 / 拓展方向，不作为当前项目功能。

讲解备注 新增角色，需要用固定样本验证

如果两个角色依赖完全相同的信息，只能串行等待，而且没有独立验收，拆分收益就需要认真验证。增加一个名字，并不会自动产生独立判断。

Reviewer 可以拥有不同的审查任务、上下文和证据要求。是否有效，应通过固定样本比较漏检、误报、人工审查负担和运行成本。仅仅换一段提示词，无法证明质量提升。

先把单个任务的输入、输出和验收写清楚，才能判断是否值得拆出新角色。并行执行还要考虑工作区冲突和汇总规则。

09 / 10选型对比

Agent 编排方案与框架选型

先指出当前重复劳动或控制需求，再选择承担它的基础设施。

Python、MAF 和 LangGraph 在本分享中的能力侧重点
方案适合承担的工作仍需业务自己定义
Python固定步骤直接表达业务顺序失败分支、状态保存与交付约定
MAFAgent 工具循环减少循环与调用样板任务契约、权限边界与完成判据
LangGraph显式状态与条件路由组织分支、等待和恢复状态语义、外部动作幂等与恢复协议

不同层的能力可以组合，选型由当前缺口决定。

当前项目 MAF 版的外层仍由 Python 顺序编排。

讲解备注 比较能力侧重点，避免把框架当成答案

这张表列出与当前问题相关的能力侧重点，不是完整的产品能力清单，也不表示三种方案互斥。固定流程、Agent 循环和图路由可以服务于不同层。

使用 MAF 不自动意味着已经实现图工作流。使用支持 checkpoint 的框架，也仍需自己定义状态内容、幂等操作和恢复后的责任判断。

选型时先描述缺口：是工具循环难维护，还是条件分支越来越多，或是必须长时间等待并恢复？再检查框架是否确实降低对应的实现和维护成本。

10 / 10现有链路交付建议

Agent 与团队工作流的集成

自动执行的结果，需要进入团队能够接手的协作入口。

SonarQube已有任务入口
Agent 执行修改、提交与创建 PR
PR / 飞书审查交付与结果通知
输入减少重复录入，带上任务上下文。
交付建议结果附带说明与可核验的证据链接。
阻塞处理明确负责人、升级路径和通知内容。

任务出现阻塞时，谁负责下一步？

交付边界：当前交付进入 PR 人工审查，由团队决定合并。

讲解备注 把技术流程接到团队责任上

SonarQube、PR 和飞书已经分别承担问题入口、审查交付和通知。自动化结果进入熟悉的入口，团队才能在原有工作流中接手。

交付信息可以进一步完善：PR 说明修改原因与范围，通知指向实际结果，有验证证据时提供链接。遇到阻塞，应写清谁来接手以及下一步需要做什么。完整证据管理是建议，不冒充当前已具备的能力。

把 Agent 作为一个有职责的执行角色：什么时候接收任务，向谁交付，失败通知谁，什么条件需要升级。可以邀请听众用自己的任务回答这些问题。
