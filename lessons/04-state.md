# 04 状态让任务有了记忆

[上一课](03-model-tool-agent.md) · [学习路线](../README.md) · [下一课](05-python-workflow.md)

## 假设进程现在退出

工单 1042 已经修改完代码，测试正在运行，电脑突然重启。

如果你只依赖屏幕上的聊天记录，新的进程怎么知道该继续测试，还是重新修改？如果测试已完成但结果没有保存，你能把任务标记成功吗？

这就是状态的用途：**把继续工作所必需的事实从短暂执行中拿出来，明确保存。**

## 先区分三种东西

**对话上下文**帮助模型理解任务，包括指令、工具结果和讨论。

**工作流状态**描述任务当前处境，例如阶段、尝试次数、等待谁、下一步候选动作。

**持久产物**是实际工作结果，例如补丁、测试日志、审阅报告，以及它们对应的代码版本。

三者会互相引用，但不要把全部内容塞进一个无限增长的聊天数组。模型需要的上下文和系统恢复需要的事实，并不完全相同。

## 一份简单状态

```python
state = {
    "task_id": "demo-1042",
    "status": "testing",
    "attempt": 1,
    "test_result": None,
}
```

`status` 回答正在做什么。`attempt` 记录这是第几次尝试。`test_result` 为空时，系统不能因为某条自然语言消息说“通过了”就假装已有测试结果。先理解这四个字段就够了。

以后，如果补丁变了但旧测试仍显示通过，我们就需要补上版本信息。第 11 课会解决这个新问题。不要为了“将来也许需要”现在就把状态设计成几十个字段。

这份 Python 字典目前只在内存里，进程退出就会丢失。它先解决“有哪些状态”的问题；第 16 课再解决“怎样把状态保存到进程之外”。

## 状态更新为什么需要规则

假设两个并行 Agent 都更新 `status`，一个写 `testing`，另一个写 `ready_for_review`。最终状态取决于谁最后写入，可能丢掉真实信息。

更稳妥的起点是：每个 worker 只写自己的结果，协调者统一做阶段转换。例如 `diagnosis_result`、`verification_result` 分开存放，只有协调者更新任务总状态。

以后可以使用数据库事务、乐观锁或框架 reducer 来处理并发；先把字段的所有者写清楚，比提前安装任何一个组件更重要。

## 最小恢复问题清单

在每个关键边界问四句：

- 这个动作开始前，已经保存了什么？
- 动作完成后，什么证据证明它发生了？
- 如果结果不确定，能否查询外部系统确认？
- 重做一次会不会造成第二次外部影响？

最后一个问题引出幂等性，我们在第 08、22 课继续展开。

## 小练习

把工单 1042 的状态写在纸上。现在假设在“补丁准备好，但测试未完成”时中断。圈出恢复时绝对不能靠猜的字段。

**带走一句话：能聊天的记忆，和能可靠恢复工作的状态，是两种不同需求。**
