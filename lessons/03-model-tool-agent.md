# 03 模型 工具 Agent 与编排

[上一课](02-control.md) · [学习路线](../README.md) · [下一课](04-state.md)

## 四个词分别指什么

**模型**接受输入并产生输出。输出可能是一段解释，也可能是符合工具调用格式的请求。模型输出“执行测试”不会让操作系统自动开始跑测试。

**工具**是程序暴露给模型或流程的能力。例如 `read_file(path)`、`run_tests(target)`。真正读文件和启动测试的是工具执行端。

**Agent**在本教程中指围绕目标运行的反馈循环：看状态、决定动作、调用工具、接收结果，再决定下一步。不同产品对 Agent 的叫法不同，因此看到这个词时要追问具体控制机制。

**编排**安排任务如何进入、分配、执行、等待、恢复和结束。它既可能控制一个 Agent，也可能控制多个 Agent，以及人类、队列和外部系统。

## 一次工具调用发生了什么

```text
模型输出：请求 run_tests，参数 target="test_amount"
运行时：检查这个工具存在且参数合法
权限层：确认当前任务允许运行这组测试
工具执行器：真正启动测试进程
运行时：把退出码和摘要交还给模型
模型：根据结果继续推理
```

你需要把“决定”与“执行”分开观察。这样才能解释两个常见问题：模型为什么明明说要做却没有做，以及工具做完了但模型为什么没有看到结果。

再把中间过程展开一点。运行时先把工具名称、说明和参数格式给模型。工具请求可以近似看成 `{"name": "run_tests", "arguments": {"target": "test_amount"}}`。模型只产生这个结构；运行时把 `name` 映射到真正的函数，检查参数，再调用函数。工具执行结果还要与这次调用关联，送回模型下一轮输入。不同 API 的实际字段不同，这里展示的是通用机制。

“自主调用工具”的自主性发生在模型选择工具与参数的那一步。可调用的名单、真实执行以及结果回传，仍由软件完成。模型如果只输出一句“我会运行测试”，却没有产生有效工具请求，就不会因此启动测试。

工具失败也应成为明确结果。例如返回 `timeout`、`permission_denied` 或结构化测试失败，不要把所有错误都变成一句“工具不可用”。不同错误需要不同处理。

## 一个 Agent 不等于一个人设

给同一个模型写三段提示词，分别叫“产品经理”“工程师”“测试专家”，不一定就得到有价值的协作。

如果它们读取相同输入、拥有相同工具、没有独立产物和验收方式，只是依次说意见，那么新增的主要是对话轮数。

真正值得分出的角色通常有明确差异：独立上下文、工具权限、责任、输出格式或验证方式。后面我们会让诊断者、实现者、验证者各自交付不同证据。

## 框架处在哪一层

可以先想象一个由下往上堆叠的系统：

1. 模型提供语言理解与决策建议。
2. 工具运行时把建议变成可控执行。
3. 编排管理步骤、状态和协作。
4. 应用提供工单入口、权限、存储、通知和界面。

真实框架可能覆盖多个层，所以产品之间不能简单一一替换。某个工具连接协议能解决“如何调用”，不意味着它同时解决“什么时候调用”和“失败后谁继续”。

## 小练习

给下面四件事分类：生成补丁、读取文件、决定再测一次、收到 Azure webhook 后创建任务。

允许一件事跨多层。例如“生成补丁”可能是模型产生文本，也可能是 Agent 使用编辑工具真正改文件。解释具体发生了什么，比贴一个词更重要。

**带走一句话：模型负责产生建议，运行时负责把建议变成受约束的行动。**
