# 产品案例阅读入口

[学习路线](../README.md) · [来源索引](sources.md)

这里比较的是有明确来源的 Meta Muse 与 `multica-ai/multica`。它们适合启发不同设计问题，不是同一层级的框架排名。

## 先按问题选一篇

- 想知道关闭界面后为什么还能继续工作：读 [Meta Muse 的主动与授权](../cases/03-meta-muse.md)。
- 想知道多个 Agent 怎样和人共用任务板：读 [Multica 的长期身份与短期 Run](../cases/04-multica.md)。
- 想知道通知丢失和旧 worker 迟到怎么办：读 [Multica 的执行可靠性](../cases/05-multica-runtime.md)。
- 想知道是谁的授权 谁的凭据 谁的电脑：读 [Multica 的权限边界](../cases/06-multica-authority.md)。

## 证据强度不同

Meta Muse 的案例来自官方产品和工程披露，未进行实测或源码审计。Multica 的案例除官方文档外，还阅读了固定提交的相关实现，但没有启动服务、运行测试或做安全审计。

“厂商说明有某能力”“源码有一条实现路径”“在特定环境测试通过”和“生产系统持续可靠”，是四个不同层次。

## 六个共同问题

1. 谁创建任务和负责收尾？
2. 谁决定下一次行动？
3. 状态存在哪里，进程退出怎么办？
4. 消息怎样送达，谁唤醒执行？
5. 哪个执行端强制检查权限？
6. 有什么证据证明任务真实完成？

答不出的部分保持未知。不要用一个产品公开的优势，补齐另一个产品没有披露的机制。

## 一个可选的局部机制

第 27 课还引用了公开项目 `qybaihe/mu` 的 hive，实现有选择地共享发现和传播更正。它只用于解释知识路由这个局部问题，并不是 Muse 或 Multica 的另一个名字。[固定版本来源](sources.md#p04)
