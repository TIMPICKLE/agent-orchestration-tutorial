# 11 让完成判断依赖证据

[上一课](10-chassis-flow.md) · [学习路线](../README.md) · [下一课](12-single-session.md)

## 停止推理以后还缺一件事

模型可能因为真的完成、没有思路、上下文不够，或者误解任务而停止。停止原因不同，不能统一等同于成功。

公开底盘中的一个关键设计是：即使编排器返回 `SUCCEEDED`，外层仍会调用 `judge` 检查完成判据。判据否决，就不能以成功收尾。[主运行器源码](https://github.com/TIMPICKLE/devops-agent-chassis/blob/63f8496eac20828f0712c8a53e2299a9b7baf8d8/src/agent_chassis/chassis.py#L177-L336)

`DoneCriteria` 可以理解为“这类任务的裁判接口”。它要回答的是任务契约是否得到满足，而不是对模型的语气打分。

## 工单 1042 的一个裁判

下面是概念代码，不是项目里已有的金额修复判据：

```python
def is_done(candidate, evidence):
    return (
        evidence.target_test_passed
        and evidence.regression_tests_passed
        and evidence.candidate_digest == digest(candidate)
    )
```

前两个条件检查功能和回归。第三个条件检查“通过测试的那份代码”是否就是现在准备交付的代码。

为什么需要第三项？假设补丁 A 通过测试，随后模型又改了一行变成补丁 B。如果还沿用 A 的通过记录，系统就会交付一份未经验证的东西。

摘要 `digest` 可以看作内容指纹。相同算法对相同内容产生相同值；内容改变时通常能通过摘要变化发现。但摘要本身不是身份签名，也不证明生成者可信。它在这里用来绑定产物与证据。

## 验收不只是执行一条测试

一个实用的测试证据最少应回答：测试什么、在哪份候选上、怎样运行、结果是什么。必要时再增加环境、日志位置和运行标识。

因此，第 04 课的简单 `test_result` 字段现在值得升级。我们不是为了设计漂亮的数据结构而加字段，是遇到了“旧证据被误用”的具体风险。

公开项目的配置策略示例检查当前候选与已验证候选的摘要一致，可作为这个思路的源码入口。[配置验收源码](https://github.com/TIMPICKLE/devops-agent-chassis/blob/63f8496eac20828f0712c8a53e2299a9b7baf8d8/payloads/config_policy.py#L45-L118)

## 验收还必须尊重任务范围

如果用户只要求准备补丁，补丁和报告齐全即可完成这个任务。你不应把“成功标准更高”当理由擅自创建 PR 或合并。

如果任务明确要求交付 PR，那么“本地测试通过”只是中间里程碑。状态和报告必须区分本地完成、PR 已创建、CI 已通过、已经合并。

## 小练习

测试通过后又改了 README，需要重跑所有测试吗？没有统一答案。先说明修改是否影响交付包、运行代码或验收范围，再写出证据失效规则。规则要明确，不能由模型临时方便地决定。

**带走一句话：完成判据检查目标和证据，并且必须知道证据属于哪份产物。**
