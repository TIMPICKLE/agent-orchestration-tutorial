# 28 按问题选择框架

## 现在才开始比较工具

你已经知道自己需要控制、状态、执行、恢复、协作和验收。现在问“哪种框架帮我减少最多重复工作”会比直接问“哪个框架最强”更有答案。

下面按主要职责比较，不是排名，也不意味着每种工具只能做表中的事。

| 方案 | 主要帮助 | 仍需你决定 |
|---|---|---|
| 普通 Python | 直接表达固定流程和小循环 | 状态保存、恢复和工具边界 |
| LangGraph | 显式图状态、路由、检查点和中断 | 业务状态、正确验收、外部副作用协议 |
| OpenAI Agents SDK | Agent、工具、专家调用、handoff 与运行控制 | 任务责任、数据权限和应用持久化设计 |
| Deep Agents | 文件、上下文和子 Agent 等工作支架 | 岗位范围、部署权限和业务生命周期 |
| Managed Agents | 托管会话和执行环境等基础设施 | 验收目标、用户授权和业务系统集成 |
| devops-agent-chassis | 可替换的任务源、编排和完成判据等接口 | 具体应用装配、真实环境验证与发布治理 |

官方入口与时效说明见 [来源索引](../references/sources.md)。

## 一个简单选择顺序

任务能用确定规则完成，就先不用模型。一次模型调用够用，就先不用循环。需要未知方向探索，再加入受限工具循环。

出现跨阶段状态、复杂路由和等待恢复时，考虑图运行时。发现独立上下文或并行专家确实改善结果时，再加子 Agent。需要常驻多人协作时，补充身份、任务管理与消息系统。

这些选择不是一次定终身。先把模型、工具和业务判据之间的接口分清，后面更容易替换某一层。

## 不同层的产品可以组合

例如 LangGraph 的修复节点内部可以使用现成 Agent harness；一个工具可以连接 MCP 服务；外层任务系统仍保存工单与审批。

MCP 解决工具和资源连接的一部分标准化问题，不能仅因使用 MCP 就推断已经有完整任务调度和多 Agent 协作。读取某个 MCP 工具，也可能完全由确定性程序发起，并不一定经过模型选择。[MCP 官方概述](https://modelcontextprotocol.io/docs/2026-07-28/getting-started/intro)

这里是在划分职责，不是鼓励把所有框架叠起来。每加一层，都应能说出它替你承担了什么，以及失败时在哪里查证据。

## 看完整应用和看框架不同

Open SWE 适合研究工程任务如何连接调查、实现、验证、PR 和反馈等阶段。它是完整应用参考，不能直接当作你每个业务的必选节点清单。[官方仓库](https://github.com/langchain-ai/open-swe)

当前框架和托管产品变化很快。先学稳定设计，再锁定依赖版本并运行小规模集成测试。公开文档示例和你机器上的已安装版本可能不同。

## 小练习

你的唯一痛点是程序重启后忘记待审批任务。应该先加两个 Agent，还是先补持久状态？写出能直接消除该失败的最小变化。

**带走一句话：选框架是为了购买具体基础设施能力，不是购买自动正确的架构。**
