# 26 评估结果而不只看演示

[上一课](25-failure-drills.md) · [学习路线](../README.md) · [下一课](27-boundaries.md)

## 怎样知道新设计更好

你把固定 Python 改成 LangGraph，再增加 reviewer。演示更丰富了，但修复质量真的改善了吗？

需要先定义评估任务，再比较变化。不要同时换模型、框架、提示词和测试集，否则很难知道收益来自哪一项。

## 先建立一个小而可检查的任务集

例如选择十个练习任务，覆盖输入解析、边界条件、错误处理和回归风险。为每个任务保存基线代码、问题说明、验收测试，以及允许动作。

十个不是统计充分性的保证，只是一个易开始的规模。任务越相似，越可能让系统对某种题型看起来很好；应逐步加入不同困难和失败类型。

对于有随机性的模型，同一任务最好运行多次。报告中说明运行次数和变化范围，不要只展示最好的一次。

## 看三个层面的结果

**目标结果。** bug 是否被正确修复？回归是否通过？产物是否真实存在且对应当前版本？

**过程约束。** 有没有越权工具调用、重复外部写入、跳过审批或把不确定结果伪装成完成？

**代价。** 耗时、模型与工具费用、人工介入时间是否值得？为了提高一点成功率，是否让人多花半小时审查？

这是一个用于本教程的评估设计。Anthropic 的 Agent 评估文章强调，应检查环境中的实际结果，而不只看对话说了什么。[官方评估说明](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

## 评分器应该各自擅长什么

程序适合检查测试退出码、文件摘要、动作是否发生。模型可以辅助分析解释是否清楚、审查是否覆盖某类风险，但它的评分也需要核对。人适合判断需求歧义、体验和业务取舍。

不要让同一个模型既修改答案，又定义唯一验收标准，再给自己打分。任务要求和关键测试应有独立来源。

## 多 Agent 的对照实验

版本 A 用单 Agent。版本 B 增加一个只读 reviewer。保持任务、模型、工具权限和预算可比较，记录 reviewer 独立发现了哪些 A 漏掉的问题。

如果 B 只是花更多时间复述已有结论，可以删除它，或缩小为仅在高风险修改时触发。撤回一个没有收益的组件，是正常工程结果。

## 小练习

写一个坏指标：“Agent 平均回复更长”。再改成与任务价值有关的指标，例如“用户能根据报告找到复现步骤和对应测试证据的比例”。

**带走一句话：评估架构时同时看结果 约束和代价，并保留单纯方案作为基线。**
