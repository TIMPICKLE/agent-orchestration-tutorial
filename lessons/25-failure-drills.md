# 25 用故障演练检查系统

[上一课](24-digital-employee.md) · [学习路线](../README.md) · [下一课](26-evaluation.md)

## 正常演示看不见很多问题

一个演示可能顺利完成：收到工单、修好代码、测试通过、报告结果。但真正的系统会遇到重复事件、迟到消息、运行中断和用户改变主意。

故障演练就是主动制造这些情况，观察系统是否仍然遵守任务契约。

## 先做四个小实验

**重复输入。** 同一个 webhook 发送两次。预期是一项业务任务被识别，不会无条件创建两个并行修改者或两条相同通知。

**旧证据。** 补丁 A 通过测试后换成 B。预期旧结果不允许 B 直接完成。

**结果未知。** 假服务创建了 PR，但响应丢失。预期系统先查询对账，不能直接断言失败并再创建一份。

**晚到批准。** 任务取消后才收到同意。预期不恢复发布，记录该回复为何不再有效。

这四个实验分别检查入口、证据、外部副作用和人类参与，覆盖不同边界。不要因为其中一个通过就宣布整体可靠。

## 一个实验怎样写清楚

```text
场景：结果通知发送成功后，保存本地确认前中断
前置：任务已完成，待发通知具有稳定消息 ID
故障点：接收服务接受后不返回响应
恢复：重新加载待发记录并查询接收服务
预期：不会形成第二条不同消息，最终记录确认结果
证据：本地状态 接收方消息数 同一消息 ID
```

这里假设接收服务支持按 ID 查询或幂等请求。如果真实平台没有能力支持这个预期，就需要调整协议或承认该边界仍有不确定性。

## 对照离线实验

[message_delivery.py](../examples/message_delivery.py) 模拟发送与响应丢失；[approval_resume.py](../examples/approval_resume.py) 模拟批准绑定与恢复。它们是学习器材，不是完整消息基础设施或认证服务。

测试已经运行哪些情形、没有运行哪些情形，见 [离线验证记录](../examples/VERIFICATION.md)。例如，重新打开数据库连接不等于真实断电演练，单消费者测试也不等于并发安全测试。

## 安全的演练方式

先用假服务和临时工作区注入故障，不要在真实通知、支付、合并或部署端点上“试试看会不会重复”。涉及不可逆动作时，测试环境要能够证明它不会触达真实目标。

## 小练习

给工单 1042 再设计一个故障：验证者超时，但实现者已经报告成功。写清系统最后应报告什么，而不是只写“捕获异常”。

**带走一句话：可靠性要用失败路径验证，不能从一次成功演示推断。**
