# 29 为现有系统规划渐进改造

[上一课](28-frameworks.md) · [学习路线](../README.md) · [下一课](30-walkthrough.md)

## 不必重写所有东西

假设你已经有一个 Python 服务，或者使用公开底盘装配了一个任务流程。最稳妥的演进不是立刻替换成一套多 Agent 平台，而是找出当前最影响可靠性的一个缺口。

下面是一条建议路线。它是本教程的改造方案，不是公开项目已经实现的生产能力列表。

如果你的任务是机械规则修复，可能一直不需要自主循环；如果只做有限只读调查，单会话可能已经足够；多人任务板则需要先解决身份和责任。先对照 [三类场景的选择](../design/scenario-decisions.md)，不要把下面路线当成每个系统都必须走完的升级阶梯。

## 第一步 固定任务契约和基线

保留现有执行方式，先记录输入、允许动作、完成标准和当前失败。建立几个能重复跑的测试任务。

对于公开底盘，可以沿已有 `TaskSource`、`RunContext`、`DoneCriteria` 接口找到插入位置。不要在模型提示词里重新实现一套与外层冲突的成功标准。

## 第二步 只开放一个探索区间

把最难写死的部分，比如定位根因和修复，交给受限单 Agent 循环。任务入口、测试门禁和交付权限保持明确。

如果使用现成单会话 harness，也把它封装成“输入任务，返回产物与证据”的执行器。这样可以比较不同执行器，而不改动所有外围流程。

## 第三步 补齐恢复与副作用

先找实际会跨很久的等待：CI、人工测试、审批。为它们保存正式状态和关联标识。再逐一检查 PR、通知和构建触发的重试语义。

公开底盘的默认 `Ledger()` 是内存；带路径时可写 JSON，但该实现不是事务数据库或分布式队列。不要把“已经有去重接口”理解成已经解决断电、多进程和外部写入问题。[账本源码与边界](../references/sources.md#r05)

## 第四步 加一个真正有价值的专家

优先选择只读、输出可验证的专家任务。比较有无该专家的差异。如果价值不明显，保留单 Agent 更简单。

只有在你能稳定处理一个 worker 的完成、失败、取消和迟到结果后，才增加更多并发角色。

## 第五步 扩展到团队工作

增加明确的请求者、owner、审批者与共享范围，建立任务面板和结果通知。此时“数字员工”才从一个运行脚本扩展为可被团队依赖的工作单元。

## 读公开配方时的一项提醒

底盘的角色配方会按固定版本读取并实例化已有项目，这与让模型从一句话自动生成任意可靠员工是不同机制。环境检查、离线文件校验和真实业务运行也是不同验证级别。[配方实例化源码](https://github.com/TIMPICKLE/devops-agent-chassis/blob/63f8496eac20828f0712c8a53e2299a9b7baf8d8/employee_factory/recipes.py#L188-L273)、[运行检查源码](https://github.com/TIMPICKLE/devops-agent-chassis/blob/63f8496eac20828f0712c8a53e2299a9b7baf8d8/employee_factory/recipe_runtime.py#L15-L114)

配方指向哪个项目，就以其公开 manifest 和固定源码为准。不要因为名字相近，随意替换成另一个实现来解释。

## 小练习

为你的系统只选一个下一步：更清楚的验收、恢复、幂等通知或独立审查。写出为什么它优先，以及怎样验证完成。

**带走一句话：一次增加一个可验证的能力，让复杂性始终有明确理由。**
