## 设计问题

如果编码 Agent 自己已经有完整研发流程知识，外层还要不要逐步指挥它怎样做需求、实现、测试和评审？

## 当前做法

这个版本把完整任务交给一个 Claude Code CLI 会话，让它在会话内组织研发步骤。外层服务主要管理任务输入、去重、进程、预算和结果记录。

```text
评论事件 → 识别与保存任务 → 补齐必要输入 → 再检查执行身份
        → 单个 CLI 会话 → 检查结果协议 → 记录终态
```

单个会话可能有多次模型和工具调用，也可能使用多份 skill。skill 是流程知识或能力说明，并不自动意味着另一个独立 Agent。

外层使用 SQLite 约束和单消费者管理任务，并有进程锁、空闲超时和总时长限制。重启恢复会区分尚在解析输入的任务和已经进入执行的任务，后者不盲目重放。这些是运行控制，不是研发阶段的逐步编排。

## 这种选择合理在哪里

对于根因未知、查阅路径多变的 bug，强行把所有调查顺序固定在外层可能束缚执行器。如果会话内已有较成熟的工作流程，减少第二套逐步指挥，可以降低控制冲突。

这种方案也更便于使用现成编码工具。外层不用重新实现每个读文件、编辑、测试的内部细节。

但收益取决于任务边界、会话能力和结果可检查性，不能仅凭代码行数减少就判定更可靠。

## 当前边界在哪里

源码中的外层结果检查会查看进程退出、结果事件与结构化报告字段；它不等于独立重跑业务测试，也不会仅凭报告中的 PR 链接证明交付正确。

任务提示允许部分研发交付动作，并要求不合并、不强推、不直接推目标分支。需要区别：数据库约束和超时由程序执行，而若干研发行为主要由提示词要求会话遵守。不能把后者写成远端权限已经硬性禁止。

服务保存状态与日志，但没有因此获得从任意内部研发步骤自动续跑的能力。若 Agent 已创建 PR 而本地尚未记下，重跑整个会话仍可能重复操作。

## 一个不夺走自主性的改造方案

**建议，尚非该版本已实现能力：**保留自主修复会话，在外面增加一个独立、只读的交付核验器。

会话提交仓库、候选 head SHA、PR 标识和测试证据引用。核验器重新读取远端 PR 状态和规定检查，确认它们属于同一仓库与当前提交。缺证据时进入阻塞或返工，不由会话自报成功结束。

如果当前政策禁止合并，就在工具网关、凭据与远端规则上使该动作真正不可用，而不是只增加一段提醒。具体能强制到什么范围，要逐条检查执行路径。

当流程进一步包含长时间构建、人工测试和版本化批准时，再考虑增加外层显式阶段。若任务止于本地补丁或只读调查，轻量会话加结果校验可能已经足够，不必为了“完整”增加整套发布状态机。

## 怎样验证

先测试三种坏报告：链接不存在、测试属于旧 SHA、模型报告成功但规定检查缺失。核验器应拒绝假完成。

再模拟 PR 创建后响应丢失，检查恢复会不会创建重复 PR。最后尝试被禁止的动作，确认执行端真的拒绝，而不只是模型碰巧没有调用。

**可以借鉴：**把未知调查路径交给一个能力合适的会话，同时保留运行预算和明确交付合同。

**不要直接照搬：**协议格式有效、进程正常退出和提示词说“不合并”，都不是完整质量或权限保证。
