# 17 增加一个 Agent 要解决什么

[上一课](16-persistence.md) · [学习路线](../README.md) · [下一课](18-manager-and-tools.md)

## 一个 Agent 已经能读 改 测

到这里，你已经能设计一个有状态、有反馈、可以暂停的单 Agent 工作流。它不因为只有一个 Agent 就不够成熟。

现在增加第二个 Agent，应该先指出一个具体问题。例如：实现者一直沿着同一个假设修复，忽略了输入格式被放宽的风险。你希望一个只读审查者从回归角度独立检查。

这个理由比“多 Agent 看起来更像公司”更值得实验。

## 三个可能有价值的理由

**任务可以真正拆开。** 一个查历史行为，一个设计测试，输入相同但输出不同，工作之间没有强依赖。

**上下文需要隔离。** 调查者可能读取很多无关日志，最后只需把证据和结论交给实现者，不必让实现者背着全部探索过程。

**权限和责任不同。** 验证者只读代码和测试结果，发布执行器只接受已批准动作。角色不只是提示词，还是能力边界。

这些是设计假设，应通过实验确认。Anthropic 的多 Agent 研究经验也提醒，高度依赖共享上下文的任务未必适合并行拆分。[官方研究系统介绍](https://www.anthropic.com/engineering/multi-agent-research-system)

## 三个常见代价

首先是交接成本：每个 Agent 都需要足够背景，摘要遗漏可能让它重复工作。其次是协调成本：意见冲突时，需要有人决定下一步。最后是运行成本：新增模型调用、等待和工具使用，不一定换来更好的结果。

因此，应先测一个清楚的收益。例如“独立审查能否发现只删逗号导致 `12,34.50` 被错误接受”。如果第二个 Agent 只是复述第一个的解释，就没有证明这个拆分值得保留。

## 独立审查怎样才更独立

把实现者的自信结论完整贴给审查者，可能让它跟随原来的判断。更好的起点是给原始需求、当前 diff、测试证据和明确的审查目标，让它先自行核对。

不过，同样的模型、相似的训练和相同盲点仍可能导致共同错误。多问一遍不能替代可执行测试，也不能证明答案独立正确。

## 小练习

写下你想加的第二个 Agent：它专门解决什么现有失败？输入和输出是什么？怎样证明比单 Agent 更好？如果无法回答，先不加。

**带走一句话：Agent 数量是设计变量，可靠性不是按人数升级的。**
